Sendr

Transactional Email Delivery Platform & Developer CLI
System Overview & Problem

Direct synchronous mail transfer (via external SMTP relays or third-party HTTP endpoints) introduces unpredictable response latencies ranging from 400ms to 5,000ms. Under heavy traffic, remote provider timeouts and strict quota throttling (HTTP 429) cause web request backpressure and silent email loss.

Sendr solves this by decoupling request intake from actual mail delivery. Incoming requests are authenticated, validated against rate-limit buckets, and committed into a transactional PostgreSQL queue within 4ms. An internal pool of concurrent goroutine workers processes queued jobs in the background, enforcing exponential backoff retries and dead-letter queueing.

Workers pull jobs concurrently using non-blocking row locks to prevent duplicate processing.
Engineering Decisions
Hexagonal Architecture

Domain business logic has zero framework imports. Chi HTTP routing and Cobra CLI serve as driving adapters; PostgreSQL and SendGrid serve as driven adapters. Enables 100% deterministic offline testing.

Postgres SKIP LOCKED Queue

Leverages SELECT ... FOR UPDATE SKIP LOCKED instead of operating a dedicated message broker cluster. Job enqueueing executes in the same atomic database transaction as the business event.

RS256 JWT + Redis Blacklist

Stateless RS256 token verification using asymmetric key pairs. Active sessions are validated against a Redis denylist to ensure immediate revocation upon logout or privilege modification.

Token-Bucket Rate Limiter

In-memory token bucket middleware evaluates per-API-key quotas to prevent downstream mail relay starvation and mitigate flood spikes before querying the database.

Trade-off: Relational Job Queue vs. Dedicated Broker
Context: Dedicated message brokers like RabbitMQ or Kafka offer higher throughput, but introduce distributed state and dual-write complexity. By utilizing PostgreSQL row locking, Sendr eliminates dual-write failures at the cost of requiring autovacuum tuning for high-churn queue tables.
Challenge: Worker Pool Graceful Termination
Context: Uncontrolled worker shutdown drops active socket connections mid-dispatch. Sendr intercepts SIGTERM/SIGINT signals, halts queue polling, and utilizes a sync.WaitGroup with a 15-second context deadline to guarantee in-flight emails either complete cleanly or roll back.

MoneyMate

7-Service Financial Microservices Monorepo & Double-Entry Ledger
System Overview & Architecture

In financial applications, mutable balance counters (e.g. UPDATE accounts SET balance = balance + 100) lead to race conditions, currency rounding discrepancies, and irrecoverable audit failures. MoneyMate is an event-driven financial platform engineered around an immutable double-entry bookkeeping engine and a decoupled 7-service Go monorepo architecture.

The system divides responsibility across 7 focused microservices:

  • API Gateway: TLS termination, reverse proxy routing, and W3C distributed trace context propagation.
  • Auth Service: Argon2id password hashing, session tokens, and role-based access control (RBAC).
  • Payment Engine: Immutable double-entry ledger where every transaction enforces equal debit and credit journal entries.
  • Merchant Service: Merchant account lifecycle, commission schemas, and settlement records.
  • Rewards Service: Asynchronous consumer calculating cashback bonuses from completed payment events.
  • Notification Service: Dispatches transaction confirmations and alerts via background Kafka topic consumption.
  • Support Service: Dispute logging against immutable ledger transaction IDs.

* Scope note: Advanced concepts like automated multi-jurisdiction tax filings and cross-currency FX arbitrage routing are deferred to future research phases and are not presented as completed features.

Engineering Decisions
Double-Entry Bookkeeping

Money balances are never stored as a single mutable integer. Account balances are mathematically derived from an immutable stream of verified credit and debit ledger entries.

Zero-ORM with SQLC

Eliminated ORM overhead by writing hand-tuned SQL compiled into deterministic, type-safe Go code with sqlc and pgx. Catches syntax and type mismatches at build time.

Transactional Outbox Pattern

Ensures at-least-once message delivery to Kafka without distributed two-phase commits. If the message broker is temporarily offline, database transactions still commit safely.

OpenTelemetry Tracing

Instruments HTTP and gRPC request flows across microservices with W3C traceparent headers, giving visibility into cross-service latency and bottlenecks.

Trade-off: Monorepo vs. Multi-Repo for 7 Services
Context: Managing 7 separate repositories requires tagging and versioning shared DTOs and protobuf definitions. Housing all 7 services in a single Go monorepo enables atomic multi-service refactors and unified CI/CD checks, while requiring strict package isolation rules to prevent leaky domain boundaries.
Challenge: Hot Merchant Account Lock Contention
Context: Concurrent transactions paying the same popular merchant would serialize on row-level balance locks. Because the ledger is append-only, write operations only insert new journal rows without locking the merchant's aggregate balance, shifting calculation overhead to asynchronous read rollups.
